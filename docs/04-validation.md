# 어떻게 검증했고 무엇이 남았나

## 테스트 개수와 업무 완성도는 달랐다

11:38 점검에서 회귀 검사 112개는 통과했지만, 제공된 공개 TC 8개는 전체 처리 완료 0개였다. 주소·발행 구분을 받는 대화가 없거나, 안전 신고가 일반 상품 질문으로 빠지는 등 검사 범위 밖의 문제가 있었다.

그 뒤부터는 모듈 테스트에 더해 실제 실패 문장을 입력하고, 필요한 질문·API·대상·값·결과 안내를 함께 확인했다. 실행하지 않은 것은 `EVIDENCE_GAP`으로 구분했다. API를 안 불렀다는 사실만으로 개인정보·쿠폰 거절 흐름까지 성공했다고 판정하지 않았다.

## 실제 카카오 공개 실습

최신 사례별 시도를 모은 기록에서 15개는 `PASS_PUBLIC_FIXTURE_REPLAY`였다. 43개 고객 응답, 평균 약 2.867말풍선/케이스, 평균 145.95자, 최대 281자였다. 원본 음성을 새로 첨부한 사례의 콜백은 약 6.378초였다.

다만 이 결과에는 세 조건이 붙는다.

1. 계정·TC·대상을 실습 설정으로 제공했다.
2. 기존 접수를 재사용했고, 초기화 후 첫 접수를 모두 재실행하지 않았다.
3. 패치 전·후의 사례별 최신 시도를 합쳤으며 같은 최종 빌드의 새 일괄 실행이 아니었다.

따라서 “최종 배포본이 15개를 실제 인증부터 전부 통과했다”는 뜻으로 쓰면 안 된다. 콜백 성공도 단말 화면 표시 시각이나 고객이 읽은 사실을 증명하지 않는다.

## 같은 조건으로 비교한 최적화

- 같은 15개 **모의** 대화: API 53→38회, 약 28.3% 감소. POST 12개는 유지했다. 접수 직전 확인과 권한 검사를 없애서 줄인 것이 아니다.
- 같은 원본 음성·warm Whisper-small CPU 작업자: 빔 3에서 1로 바꿔 10.937→5.665초. 환불 문의 핵심은 보존됐지만 방언 전체의 단어 오류율이 같다고 검증하지는 않았다.
- 명확한 SKU·가격 비교는 검색한 공개 자료를 직접 사용했다. 일부 로컬 즉답은 밀리초 단위였지만 이를 카카오 전체 응답 시간으로 표시하지 않았다.

## 모델·첨부 검증

원본 음성 파일을 STT로 읽는 검사와, 카카오에 새로 첨부한 파일을 자동 인식하는 검사를 따로 진행했다. 사진도 원본 URL의 모델 판독 성공과 실제 카카오 인입을 구분했다. 일반 상담 전환 후 사진 모델 처리 2.859초가 관찰됐지만, 사진 확인이 곧 본인 주문 인증이나 환불 성공은 아니다.

## 최종 정리 시점의 상태

14:43 요청 구조 패치 시점에는 252개 회귀 검사가 통과했다. 이후 실습 전용 소스와 해당 검사를 정리했고, 독립 음성 예외 검사를 보존한 최종 결과는 **245개 통과**였다. 숫자가 줄어든 것을 실패로 숨기거나, 이전 숫자를 최종 결과처럼 쓰지 않았다.

14:54:39 정리 결과에는 백업 확인, 예외 검사 7개, 게이트웨이 READY가 기록됐다. **정리 후 실제 카카오 전체 대화 재검증은 하지 않았다.** 또한 최종 실제 요청에서 공식 인증 정보·TC ID 경로는 확인되지 않았다.

공개용 근거 파일은 [summary.json](../evidence/summary.json)과 [source-manifest.json](../evidence/source-manifest.json)에 있다. 원본 로그·회원·접수 데이터는 공개하지 않았다. 이 문서는 당시 검증 결과를 재검토한 기록이며 지금 외부 API를 다시 실행한 결과가 아니다.
