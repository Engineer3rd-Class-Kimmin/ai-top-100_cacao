# 10시부터 15시까지

당일에는 자료를 조사하는 일과 상담 봇을 만드는 일이 동시에 진행됐다. 이 문서는 두 채팅을 시간순으로 맞춰 다시 쓴 기록이다. 시각은 KST이며, 채팅 요청 시각과 결과 보고 시각을 구분했다. 표의 구간은 이해를 위한 묶음이고, 그 구간 내내 한 가지 작업만 했다는 뜻은 아니다.

## 시작 전에 준비돼 있던 것

10월 1일부터 범용 Agent Harness를 만들었고, 이후 누락 데이터에 대한 역질문과 같은 작업 재개 기능을 보강했다. 10월 28일에는 카카오에서 CSV 데이터의 누락값을 보완하고 계산을 재개하는 Mock 흐름을 확인했다.

따라서 당일 10시의 출발점은 빈 폴더가 아니었다. 파일 읽기, Planner·Executor·Verifier, 상태 저장, 카카오 게이트웨이는 있었지만, 교동마을의 업무 지식과 실제 상담 액션은 아직 부족했다. 이 준비 기간을 당일 5시간의 성과에 섞지 않았다.

## 10:00~11:00 — 상담 문장보다 운영 기준부터

10:03 문제 안내를 확인하며 과제를 “산지직송 고객 상담 + 실제 업무 처리”로 해석했다. 운영자에게 자료와 모든 연락처를 한꺼번에 요청했지만, 답변은 업무 하나로 범위를 좁혀 달라는 것이었다. 첫 주제를 주문 취소·환불로 정했다.

10:06 판매·환불 규정과 결제·주문 대사 절차를 읽었다. 결제됐다는 고객 말과 실제 주문 상태를 분리하고, 접수와 지급 완료도 구분해야 했다. 문서가 별도 산식을 참조하면 그 원본을 찾았다. 운영자가 모르는 자료를 계속 요구하지 않고 배송 담당자와 조합장으로 연결했다.

10:11~10:26에는 배송 계약, 집하·인계 기록, 기사 수첩, 온도 로그와 위탁 계약을 함께 봤다. “인계 시점 온도 정상”과 “운송 중 이탈 없음”이 같은 말이 아니라는 점이 중요했다. 한 번의 정상 수치보다 시간에 따른 기록과 책임 경계를 확인했다.

10:30~10:32에는 위임 권한과 부분환불 산식을 확인했다. 비율을 판정하기 전의 반올림, 금액 절상, 최소 환불액과 경계값은 Python으로 계산했다. 일반 재량 한도만 보고 명백한 하자의 전액환불까지 막지 않도록 예외를 따로 기록했다.

액션 API는 모델이 주소를 만들어 호출하게 하지 않았다. 10:35 이후 명세 파일을 받아 연결 코드를 준비했고, 토큰과 사례 정보가 없을 때는 오프라인 계약 검증부터 했다. 토큰을 찾는 화면을 잘못 안내한 시행착오도 있었다. 실제로 확인한 문서 내용과 추측을 더 일찍 나눴어야 했다.

## 11:00~12:00 — 자료를 상담 흐름으로 바꾸기

11:00 무렵 액션 토큰 설정을 확인했고, 11:11 로컬 Qwen 모델을 고객 응대에 연결한 결과가 보고됐다. 동시에 인터뷰에서는 홍보·체험·조합원 자료를 확보했다. 광고 문구와 상세페이지가 다른 경우, 광고를 사실로 따라가기보다 공식 조건과 오해에 대한 사과·정정 요청을 나눴다.

11:21부터 시작한 별도 구현 채팅에서는 곰팡이 수박 사례를 우선 처리했다. 안전 확인, 대상 주문, 증빙, 고객 선택, 환불과 안전 이관이 한 흐름 안에 있어야 했다. 주문번호를 문서의 예시 숫자로 채우면 다른 주문을 처리할 수 있어, 일단 멈추고 대상을 확인했다.

11:38의 공개 TC 점검은 중요한 전환점이었다. 회귀 검사는 112개가 통과했지만, 제공된 8개 사례의 전체 처리는 완료되지 않았다. 주소 변경과 영수증 발행 흐름이 없고, 배상 요구는 일반 상품 문의로 빠졌으며, 쿠폰 거절과 타인 주문 요구의 필수 설명·이관도 부족했다.

이후 “테스트가 통과하니 기능도 완성됐다”는 판단을 버리고, 각 실패 대화를 재현하는 검사를 추가했다. 11:44에는 8개 사례의 모의 인증·HTTP 흐름을, 11:55에는 추가 7개를 포함한 15개 흐름을 확인했다. 이때는 아직 새 음성 첨부나 카카오 전체 대화를 검증한 것이 아니었다.

인터뷰 쪽에서는 계약서, 프로모션 원장, 라이브 기록을 구분했다. 11:47에는 실제 프로모션 조회를 확인했다. 할인 코드와 보상 쿠폰의 중복 규칙을 광고 이미지 한 장으로 단정하지 않고 원장과 계약을 확인했다.

## 12:00~13:00 — 실제 경로와 지연 시간을 확인

12:05 시작한 실검증에서는 서버를 띄우고 사용자가 실제 카카오로 문장을 보냈다. 원본 음성의 인식, 재출고 API 접수, Qwen 상품 답변과 콜백을 대조했다. 같은 접수의 재요청에서는 기존 번호를 재사용했다. 이 과정에서 과거 결항 날짜를 현재 일정처럼 표현하는 문제를 수정했다.

새로 첨부한 음성을 받았을 때는 한 번 주문번호 질문으로 빠졌다. 이후 실제 인식 경로를 확인하고, 환불 문의의 요지는 되짚되 하자인지 단순 변심인지 다시 묻게 했다. 음성에 불명확하게 나온 주문번호를 추정해서 쓰지 않았다.

12:36에는 최적화 결과를 보고했다. 완료된 접수 뒤의 반복 조회를 줄이고, 명확한 SKU 질문은 모델 없이 근거를 직접 사용했다. API·모델 대기 동안 DB 쓰기 잠금을 잡지 않고 대화별로 실행을 분리했다. Whisper는 매번 로딩하지 않고 상주시켰다. 같은 모의 대화의 호출 수와 같은 원본 음성으로 전후를 비교했다.

이 시간에도 자료 수집은 계속됐다. SKU, 라벨, 자연감량 기준, 달력, 구독 약관과 영수증 규정을 확보했다. 규정별로 기준일과 처리 창구가 달랐으므로, 일반 규칙 하나로 모두 덮지 않도록 정리했다.

## 13:00~14:00 — 15개 실습과 일반 상담의 차이

13:02에는 최신 자료 반영과 189개 회귀 검사 결과를 확인했다. 다만 실제 전체 검증에 필요한 인입 계정과 주문이 빠진 사례가 남아 있었다. 사용자가 공개 TC 화면의 상담 정보를 전달했고, 그 범위에서 회원과 주문 후보를 좁혔다. 같은 조건의 주문이 두 건인 경우는 자동 선택하지 않았다.

13:18에는 L-03부터 카카오 실습을 시작했다. 주소는 사용자가 승인한 가상 테스트 주소를 사용했고, 음성 사례에서는 원본 M4A를 실제 첨부했다. 실패를 모아 패치한 후 L-34·L-40·R-05-a를 재전송했다. 13:40:42에 저장된 결과는 사례별 최신 시도 15개가 처리 기준을 충족한 집계다. 동일 빌드에서 상태를 초기화한 일괄 재실행은 아니었다.

13:41에는 고정 계정·주문에 의존하는 공개 실습 모드를 끝내고 일반 상담 모드로 전환하기 시작했다. 여기서 가장 큰 문제가 드러났다. 카카오의 사용자 식별자는 알 수 있었지만, 그것을 대회 가상 회원의 로그인 세션에 연결하는 공식 형식을 확인하지 못했다. 실습에서 공급했던 정보가 일반 요청에도 들어온다고 가정할 수 없었다.

한편 수집 채팅에서는 13:25 마지막 관계자의 채널을 찾았고, 13:27까지 10명 모두와의 대화를 확인했다. 방송 발언의 존재와 혜택을 승인할 권한은 별개로 정리했다.

## 14:00~15:00 — 예외 수정과 남은 연결 한계

14:02 전체 워크플로우를 점검하면서 인증·사진 연결의 공백과 코드 오류 5개를 구분했다. 재배송 거부 문장에서 접수가 일어나는 문제, 환불 성공 뒤 이관 실패가 전체 실패로 보이는 문제, 만료된 보상 코드, 미구현 환불 선택지, 이전 계정 업무에 갇힌 공개 문의가 대상이었다.

14:28 이후 패치·배포 결과에서 회귀 검사 231개와 실제 카카오 응답을 구분해 보고했다. 새 사진의 실제 인식은 확인했지만, 인증된 계정 업무의 성공으로 확대하지 않았다.

자료 쪽은 14:03 기준 발굴률 표시의 단순 평균이 45.8%였고, 이후 확인에서도 같았다. 14:08 가격 캡처 14장을 대조했고, 14:17 축제 전단에서 온라인과 다른 현장 구매 정책을 보강했다. 14:25:04에 만든 통합 전달 파일은 확인 상태와 미확인 사항을 함께 담았다. 파일 생성 뒤에는 검색 엔진이 실제로 읽은 번들 해시까지 대조했다.

14:43:43 마지막 요청 구조 검증 보고서를 남겼다. 발화와 사용자 ID를 분리하고, TC ID나 상담일시를 임의로 만들지 않도록 했다. 실제 카카오 응답 3건은 성공했지만 인증 정보가 없어 액션은 0건이었다.

14:50:29~14:54:39에는 요청에 따라 실습 전용 코드 13개를 백업 후 제거했다. 회귀 검사 245개와 예외 검사 7개를 확인하고 게이트웨이 READY를 확인했다. 정리 후 실제 카카오 전체 대화는 다시 검증하지 않았다. 사용자가 제출을 위해 작업 종료를 요청한 뒤에는 추가 변경을 중단했다. 실제 제출 버튼 조작과 공식 채점 결과는 이 기록의 검증 범위 밖이다.

## 5시간을 돌아보면

가장 오래 걸린 부분은 문장을 생성하는 일이 아니라, 근거와 권한의 경계를 알아내는 일이었다. 자료는 계속 늘었지만 어떤 정보가 실시간 요청으로 들어오는지는 끝까지 확인하지 못했다. 다시 한다면 첫 30분 안에 “실제 카카오 요청 한 건에서 회원·TC·기준일을 어떻게 받는가”부터 검증하고, 그 결과에 맞춰 업무 범위를 정할 것이다.
