# 잘된 점과 끝내 해결하지 못한 점

## 잘했다고 생각하는 것

가장 의미 있었던 것은 답변을 잘 만드는 문제와 실제 업무를 처리하는 문제를 나눠 본 점이다. 고객에게 “이관했습니다”라고 말해도 접수 기록이 없으면 일을 끝낸 것이 아니었다. 반대로 환불 접수는 됐는데 뒤의 안전 이관이 실패했다면, 이미 된 일까지 없었던 것처럼 답해서도 안 됐다.

자료를 다루는 방식도 중간에 구체화됐다. 문서 요약만 남기면 적용 시점이나 예외가 빠지기 쉬웠다. 원본, 확인 상태, 조건과 미확인 사항을 함께 보관하고, 엔진이 실제로 그 버전을 읽었는지 해시로 확인했다. 두 채팅에서 병행한 작업을 파일 하나로 넘기는 데 그치지 않고 런타임까지 확인하려 했다.

속도는 모델을 더 빨리 돌리는 것만으로 풀지 않았다. 모델을 부를 필요가 없는 질문을 골라내고, 이미 끝난 접수 뒤의 반복 조회를 줄였다. 부족한 정보를 한 번에 묻고 실패한 단계부터 이어가는 것이 고객의 대화 횟수와 처리 시간 모두에 도움이 됐다.

## 가장 큰 한계는 인증 연동이었다

공개 TC 실습에서는 계정·TC·주문 정보를 알고 있었다. 그 환경에서 처리 흐름이 성공했다고 해서, 심사관이 일반 카카오 메시지를 보냈을 때도 같은 정보가 제공되는 것은 아니었다.

일반 상담 모드로 전환하면서 이 차이가 드러났다. 실제 카카오 요청에는 대화 식별자와 발화가 있었지만, 조합몰 회원과 연결되는 인증 정보나 공식 TC 전달 필드를 확인하지 못했다. 서버 소유 컨텍스트와 서명 어댑터는 구현했지만, 정보를 공급할 공식 상류 경로는 연결하지 못했다.

그래서 마지막 요청에서는 일반 안내는 하되 계정 액션을 차단했다. 잘못된 주문 처리 방지는 필요하지만, 심사에서 요구하는 조회·환불을 수행하지 못할 위험이 남았다. 이를 “안전하므로 완성”이라고 볼 수는 없다. 이 포트폴리오는 실제 심사 성공을 주장하지 않는다.

다시 한다면 초반에 아래 한 흐름부터 끝까지 확인할 것이다.

> 실제 카카오 요청 수신 → 인증된 회원 컨텍스트 확보 → 고객이 확인한 주문 조회 → 허용된 접수 → 접수번호 안내

이 계약이 확인되지 않으면 기능을 넓히기 전에 문서·운영진 확인과 테스트 입력 형식을 우선 정해야 한다. 지금의 서명 어댑터는 해결책 후보이지, 공식 연동 완료의 증거가 아니었다.

## 질문을 더 많이 하는 것과 더 알아내는 것은 달랐다

자료 이름이 참조돼 있다고 그 관계자가 원본을 갖고 있는 것은 아니었다. 이미 모른다고 답한 내용을 변형해서 다시 묻거나, 소개가 되돌아오는 경로를 반복하며 시간이 소모됐다.

후반에는 한 질문을 한 업무로 좁히고 확인 불가 경로를 종료했지만, 더 일찍 했어야 했다. 질문 전후 `./status`를 기록했어도 어느 질문이 증가에 기여했는지는 모두 연결하지 못했다. 최종 확인 평균 45.8%는 성과이면서 동시에 수집 전략을 더 개선할 여지가 있다는 수치다. 다른 참가자와의 상대 순위나 점수로 환산할 수는 없다.

## 검증 결과를 설명하는 방식도 바꿔야 했다

당시 보고에서는 “공개 TC 15개 통과”라는 표현 뒤에 실습 조건을 붙였다. 하지만 첫 문장만 보면 최종 일반 상담 모드까지 완료됐다고 받아들일 수 있었다. 이후 대화에서 이 차이를 다시 설명해야 했다.

다음에는 결과 이름부터 나누겠다. “고정 컨텍스트 실습 성공”, “최종 일반 상담 응답 성공”, “인증된 액션 E2E 미검증”을 별도 항목으로 두고, 마지막 배포 버전과 연결하겠다. 테스트 개수나 콜백 성공 수를 기능 완성도의 대체 지표로 쓰지 않겠다.

## AI 도구와 내가 한 일

이 작업은 AI 도움 없이 혼자 모든 코드를 작성한 사례가 아니다. AI 코딩 도구를 사용해 문서를 분석하고 질문 후보를 만들었으며, 코드·테스트·패치를 작성하고 실행 결과를 정리했다. 두 채팅은 각각 자료 수집과 엔진 구현을 중심으로 진행됐다.

나는 실제 관계자 대화를 전송하고 답변·자료를 전달했으며, 공개 TC와 테스트 대상을 확인하고 카카오에서 재현 메시지와 첨부를 보냈다. 요구사항과 우선순위를 정하고, 일반 사용자 접근과 인증 차단의 경계를 결정했으며, 제출 전 작업 종료를 요청했다.

포트폴리오에서는 이 협업 방식을 숨기지 않는다. 남은 가치는 코드 줄 수보다 무엇을 근거로 판단했고, 어떤 실패를 실제로 재현했으며, 아직 검증하지 못한 것을 어디까지 인정했는지에 있다고 생각한다.

## 다음 시도에서 바꿀 순서

1. 첫 30분에 실제 인입·인증·TC·기준일 계약과 최소 접수 흐름을 확인한다.
2. 인터뷰 질문의 증가분과 업무 영향을 함께 기록하고, 막힌 경로의 반복을 줄인다.
3. 대표 사례를 실제 경로로 일찍 끝낸 뒤 사례 수를 늘린다.
4. 테스트 결과를 모의·실접수·카카오·최종 빌드로 처음부터 분리한다.
5. 마감 직전 구조 변경을 줄이고, 최종 배포본의 재검증 시간을 먼저 확보한다.
